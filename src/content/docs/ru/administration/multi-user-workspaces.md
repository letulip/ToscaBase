Однопользовательский workspace (рабочее пространство; см. [Настройка workspace и проекта](/ToscaBase/ru/getting-started/workspace-and-project-setup/)) обслуживает одного человека в один момент времени. Когда команда работает с одними и теми же Module, TestCase и ExecutionList, каждому участнику нужен собственный workspace, подключённый к **общему репозиторию** (common repository) — базе данных, где хранится эталонная копия каждого объекта. Это и есть многопользовательский workspace. С ним появляются цикл check-out/check-in (взятие на редактирование/возврат), экран входа, управление пользователями, ветки, версионирование и Test mandates. Этот документ описывает создание, ежедневный цикл check-out и Synchronization policy; остальному посвящены отдельные документы раздела.

## Типы репозитория

При создании workspace поле **Type of repository** определяет, что вы получите:

| Репозиторий | Результат | Данные подключения |
|---|---|---|
| `None` | Однопользовательский workspace | не нужны |
| `SQLite` | Многопользовательский workspace на локальной базе | не нужны: ни строки подключения, ни схемы |
| `Oracle`, `MS SQL Server`, `DB2` | Многопользовательский workspace на выделенном сервере БД | **строка подключения** (пользователь, пароль, адрес базы) обязательна, **схема** необязательна (уроки 40 и 90); перед созданием нажмите **Test connection** |

:::caution
SQLite предназначен для практики и знакомства с многопользовательскими функциями. Для реального проекта это не решение: реальному проекту нужен выделенный экземпляр Oracle, MS SQL Server или DB2.
:::

## Создание многопользовательского workspace

1. В Tosca Commander выберите **Create new** workspace.
2. Установите **Type of repository** в `SQLite` (либо тип БД и её строку подключения; проверьте подключение).
3. Выберите папку и задайте имя workspace (в источнике — `MultiDemo`).
4. Включайте **Slim workspace** только для большого репозитория: он занимает меньше места и работает быстрее.
5. Для первого workspace оставьте **Use existing repository** выключенным — тогда Tosca создаст репозиторий (с включённой опцией она отказывается работать с ещё не существующим репозиторием). Включайте его для каждого следующего workspace на том же репозитории (второй участник команды или [ветка](/ToscaBase/ru/administration/branches/)).
6. Нажмите **OK**. Создание занимает некоторое время, затем workspace открывается.

## Экран входа и пользователь по умолчанию

Многопользовательский workspace всегда запрашивает имя пользователя и пароль. В только что созданном workspace Tosca уже завела одного пользователя `Admin` с пустым паролем: введите `Admin`, оставьте пароль пустым и нажмите **Login**. Реальных пользователей создайте затем, как описано в [Пользователи и группы](/ToscaBase/ru/administration/users-and-groups/).

:::note
Уроки по Tosca 16 расходятся насчёт первого входа. В уроке 40 вход выполняется как `Admin` с пустым паролем, как и в уроке 90; в уроке 42 диалог создания просит имя и пароль администратора, пока создаёт новый репозиторий, и этот пользователь используется на экране входа. Если ваша версия спрашивает — вводите заданные там данные.
:::

## Check-out и check-in

Каждый объект репозитория либо свободен, либо взят на check-out вами, либо кем-то другим:

- **Зелёная метка** перед объектом означает, что он взят на check-out вами. Редактировать можно только такие объекты; у свободной папки в контекстном меню вообще нет пунктов **Create**.
- **Красная полоса** перед объектом означает, что его держит другой пользователь. Изменить его нельзя, пока тот не сделает check-in.

Сразу после создания все папки проекта зелёные: создавший workspace пользователь держит всё. Один раз выполните **Check In All**, прежде чем начнут работать остальные, иначе они видят структуру, но ничего не могут менять (урок 40).

Пока объект у вас, никто другой не может его менять: в отличие от Git, Tosca не сливает параллельные правки одного объекта, а не допускает их, поэтому конфликтов разрешать не приходится. Правки разных пользователей в разных объектах сливаются при check-in.

Четыре операции, доступные на панели многопользовательского раздела и в контекстном меню каждого объекта:

| Операция | Эффект |
|---|---|
| **Update All** | Забирает в ваш workspace все изменения, которые другие пользователи сдали через check-in. Делайте это перед началом работы; TCShell умеет автоматизировать это ([Инструменты командной строки](/ToscaBase/ru/administration/command-line-tools/)). |
| **Checkout** | Берёт на check-out только один объект, например папку `Execution`, но ничего внутри неё. |
| **Checkout Tree** | Берёт объект и всё его содержимое. Используйте на папке, которую собираетесь переработать, чтобы никто тем временем не менял её содержимое. |
| **Check In All** | Сдаёт все объекты, которые вы держите, и делает ваши изменения доступными остальным. Делайте это по окончании работы. |

Рекомендуемый ритм: **Update All**, check-out нужного (**Checkout Tree** для папки, которую перерабатываете), работа, **Check In All**. При закрытии workspace с взятыми на check-out объектами Tosca предлагает сделать check-in; **No** оставляет их взятыми в репозитории.

## Кто изменил, кто держит

Щёлкните любой объект правой кнопкой (работает и для администратора, и для обычного пользователя):

- **Show latest change details** показывает имя объекта, время последнего изменения и пользователя, который его сделал.
- **Show checkout details** показывает, когда объект взят на check-out, каким пользователем и имя объекта. Если вам нужен объект с красной полосой, отсюда понятно, к кому обратиться.

## Отзыв checkout

Забрать взятый объект у другого пользователя может только член группы `Admins` (пользователь по умолчанию `Admin` в неё входит). Щёлкните объект правой кнопкой и выберите **Revoke checkout**. Tosca предупредит, что все изменения в объекте будут отброшены: всё, что другой пользователь сделал, держа объект, теряется, даже если он потом сделает check-in. После **OK** объект снова свободен; возьмите его на check-out сами, чтобы работать.

## Synchronization policy

**Synchronization (синхронизация)** — процесс, который держит объекты вашего workspace в соответствии с изменениями в общем репозитории; запускает его **Update All**. В больших репозиториях синхронизируются не все папки: чтобы workspace открывался и обновлялся быстрее, папки, которые большинству тестировщиков не нужны, намеренно **исключают из синхронизации**, и каждый тестировщик включает только те папки, с которыми работает.

Исключённая папка выглядит заблокированной, но это не так:

- папка и объекты внутри неё остаются серыми после **Update All**;
- **Checkout** в контекстном меню недоступен, а **Checkout Tree** сообщает, что объектов для check-out нет;
- внутри неё нельзя ничего создать, изменить или взять на check-out.

Чтобы получить доступ, щёлкните объект правой кнопкой и выберите **Include for synchronization** (объект) или **Include all necessary items for tree** (вместе с дочерними); папка становится рабочей. **Exclude from synchronization** и **Exclude tree from synchronization** делают обратное: объект (или поддерево) становится серым и со следующего check-in не синхронизируется.

Что можно исключать, определяет свойство **Synchronization policy** на панели Properties взятого на check-out объекта:

| Значение | Смысл |
|---|---|
| `Customizable, default is on` | По умолчанию. Синхронизируется, но любой пользователь может исключить объект |
| `off` | Не синхронизируется |
| `Cannot be excluded` | Синхронизируется всегда; исключить объект никто не может |
| `Cannot be excluded for whole tree` | Объект и все его дочерние объекты нельзя исключить |

Объекты, создаваемые внутри родителя, наследуют его значение. Экспорт или импорт объекта сбрасывает свойство в `Customizable, default is on`.
