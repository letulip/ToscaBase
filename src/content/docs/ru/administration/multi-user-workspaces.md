Однопользовательский workspace (рабочее пространство; см. [Настройка workspace и проекта](/ToscaBase/ru/getting-started/workspace-and-project-setup/)) может использовать один человек в один момент времени. Когда команда работает с одними и теми же Module, TestCase и ExecutionList, каждому участнику нужен собственный workspace, подключённый к **общему репозиторию** (common repository) — базе данных, где хранится эталонная копия каждого объекта. Это и есть многопользовательский workspace. С ним появляются цикл check-out / check-in, экран входа, управление пользователями, ветки, версионирование и test mandate — ничего этого в однопользовательском workspace нет. Этот документ описывает создание workspace и ежедневный цикл check-out; остальным возможностям посвящены отдельные документы раздела.

## Типы репозитория

При создании workspace поле **Type of repository** определяет, что вы получите:

| Репозиторий | Результат | Данные подключения |
|---|---|---|
| `None` | Однопользовательский workspace | не нужны |
| `SQLite` | Многопользовательский workspace на локальной базе | не нужны: ни строки подключения, ни схемы |
| `Oracle`, `MS SQL Server`, `DB2` | Многопользовательский workspace на выделенном сервере БД | строка подключения (содержит пользователя, пароль и адрес базы); схема необязательна; перед созданием нажмите **Test connection** |

:::caution
SQLite предназначен для практики и знакомства с многопользовательскими функциями. Для реального проекта это не решение: реальному проекту нужен выделенный экземпляр Oracle, MS SQL Server или DB2.
:::

## Создание многопользовательского workspace

1. В Tosca Commander выберите **Create new** workspace.
2. Установите **Type of repository** в `SQLite` (либо тип БД и её строку подключения; проверьте подключение).
3. Выберите папку и задайте имя workspace (в источнике — `MultiDemo`).
4. Оставьте **Slim workspace** выключенным, если в репозитории нет большого объёма данных. Slim workspace занимает меньше места и ускоряет большой репозиторий; для маленького автор предпочитает обычный workspace.
5. Оставьте **Use existing repository** выключенным, если это первый workspace на данном репозитории, — тогда Tosca создаст репозиторий. Включайте его для каждого следующего workspace, который должен подключиться к тому же репозиторию (второй участник команды или workspace на [ветке](/ToscaBase/ru/administration/branches/)).
6. Нажмите **OK**. Создание занимает некоторое время, затем workspace открывается.

:::note
Формулировка автора об опции **Use existing repository** в уроке 90 противоречива; описанное выше поведение — то, что показывают демонстрация и продолжение в уроке 92: опция недоступна, пока репозитория нет, и включается потом.
:::

## Экран входа и пользователь по умолчанию

Многопользовательский workspace всегда запрашивает имя пользователя и пароль. В только что созданном workspace Tosca уже завела одного пользователя `Admin` с пустым паролем: введите `Admin`, оставьте пароль пустым и нажмите **Login**. Реальных пользователей создайте затем, как описано в [Пользователи и группы](/ToscaBase/ru/administration/users-and-groups/). Учётные данные чувствительны к регистру.

## Check-out и check-in

Каждый объект репозитория либо свободен, либо взят на check-out вами, либо кем-то другим:

- **Зелёная метка** перед объектом означает, что он взят на check-out вами. Редактировать можно только такие объекты; у свободной папки в контекстном меню вообще нет пунктов **Create**.
- **Красная полоса** перед объектом означает, что его держит другой пользователь. Изменить его нельзя, пока тот не сделает check-in.

Пока объект у вас, никто другой не может его менять. В этом главное отличие от репозитория кода вроде Git: Tosca не сливает параллельные правки одного объекта, а не допускает их, поэтому конфликтов разрешать не приходится. Изменения разных пользователей в разных объектах сливаются при check-in.

Четыре операции, доступные на панели многопользовательского раздела и в контекстном меню каждого объекта:

| Операция | Эффект |
|---|---|
| **Update All** | Забирает все изменения, которые другие пользователи сдали через check-in, и сливает их в ваш workspace. Делайте это перед началом работы. Автоматизируется через TCShell, см. [Инструменты командной строки](/ToscaBase/ru/administration/command-line-tools/). |
| **Checkout** | Берёт на check-out только один объект, например папку `Execution`, но ничего внутри неё. |
| **Checkout Tree** | Берёт объект и всё его содержимое. Используйте на папке TestCase, которую собираетесь переработать, чтобы никто тем временем не менял её содержимое. |
| **Check In All** | Сдаёт все объекты, которые вы держите, и делает ваши изменения доступными остальным. Делайте это по окончании работы. |

Рекомендуемый ритм: **Update All**, check-out нужного (tree для папки, которую перерабатываете), работа, **Check In All**. При закрытии workspace с взятыми на check-out объектами Tosca предлагает сделать check-in; ответ **No** оставляет их взятыми в репозитории — об этом следующий раздел.

:::tip
Папка, которая остаётся серой после **Update All**, у которой **Checkout** недоступен, а **Checkout Tree** сообщает, что брать нечего, — не заблокирована другим пользователем: она исключена из синхронизации. См. раздел о Synchronization policy в [Синхронизация вместо ожиданий](/ToscaBase/ru/best-practices/synchronisation-not-waits/).
:::

## Кто изменил, кто держит

Щёлкните любой объект правой кнопкой (работает и для администратора, и для обычного пользователя):

- **Show latest change details** показывает имя объекта, время последнего изменения и пользователя, который его сделал.
- **Show checkout details** показывает, когда объект взят на check-out, каким пользователем и имя объекта. Если вам нужен объект с красной полосой, отсюда понятно, к кому обратиться.

## Отзыв checkout

Только член группы `Admins` может забрать взятый объект у другого пользователя. Щёлкните объект правой кнопкой и выберите **Revoke checkout**. Tosca предупредит, что все изменения в объекте будут отброшены: всё, что другой пользователь сделал, держа объект, теряется и не будет слито, даже если он потом сделает check-in. После **OK** объект снова свободен; возьмите его на check-out сами, чтобы работать.
