Большинство реальных API отклоняют запрос без учётных данных. В Tosca API Scan у каждого сообщения есть настройка **Authentication (аутентификация)**, где вы выбираете механизм, ожидаемый API, и вводите учётные данные; протокол Tosca берёт на себя. Источники демонстрируют Basic и Digest; остальные механизмы перечислены для полноты.

## Доступные механизмы

Выпадающий список аутентификации сообщения предлагает, среди прочего:

| Механизм | Что вводится | Примечание |
|---|---|---|
| Basic | Имя пользователя, пароль | Самый распространённый |
| Digest | Имя пользователя, пароль | Тот же ввод, что у Basic; внутри — многошаговый обмен с хешированием |
| OAuth 2.0 | На основе токена | Упомянут в источнике, не показан |
| NTLM | Учётные данные Windows | Упомянут в источнике, не показан |
| Kerberos | Учётные данные Windows | Упомянут в источнике, не показан |

Выбирайте тот, что указан в документации API: отправка Basic-учётных данных на endpoint под Digest не авторизует запрос, хотя ввод выглядит одинаково.

## Basic-аутентификация

1. Создайте сообщение (в источнике `Basic auth` в папке `Authentication`) и укажите endpoint защищённого ресурса. В демо используется сервис Postman Echo, `postman-echo.com/basic-auth`, но подойдёт любой API, защищённый именем пользователя и паролем.
2. Сначала запустите **без** аутентификации. Ответ — статус `401 Unauthorized` с payload `Unauthorized`: сервер требует учётные данные в запросе, прежде чем ответить.
3. Вернитесь на вкладку **Request**, выберите аутентификацию **Basic**, введите **username** и **password**.
4. Запустите снова. Статус теперь `200`, а payload сообщает `authenticated: true`.

## Digest-аутентификация

Со стороны клиента Digest выглядит точно как Basic: выбираете **Digest**, вводите имя пользователя и пароль, запускаете. Разница — в том, что происходит на проводе:

1. Клиент (Tosca) отправляет запрос.
2. Сервер отвечает `401 Unauthorized`, но его заголовок `WWW-Authenticate` несёт **realm** и **nonce**.
3. Клиент отправляет запрос повторно с заголовком `Authorization`, в котором учётные данные **захешированы** с использованием этих значений, так что пароль не передаётся открытым текстом.
4. Сервер проверяет хеш и отвечает `200` с payload.

Итого обмен состоит из двух запросов и двух ответов вместо одной пары. Tosca выполняет весь обмен внутри; в API Scan виден только финальный `200`.

В демо используется пример сервиса Tricentis, защищённый Digest (API «secured employee», версия 2, на хосте веб-сервисов Tricentis). Без аутентификации он возвращает `401`; с **Digest** и учётными данными примера — `200` и данные сотрудника.

:::note
Точный URL примера сервиса в транскрипте неразборчив. Берите его со страницы API-сервисов Tricentis, а не из этого документа.
:::

## Где ещё встречаются учётные данные

- **Токен из запроса логина.** Некоторые API выдают токен в ответ на запрос логина, который затем отправляется header-параметром с каждым другим запросом. В TestCase токен буферизуется из ответа логина, а буфер подставляется в заголовок следующих запросов; разобранный пример — в [TestCase для API](/ToscaBase/ru/api-testing/api-test-cases/).
- **Сканирование защищённого определения.** Секция **Advanced** диалога сканирования принимает имя пользователя и пароль (и настройки прокси) для самого файла определения; см. [Основы API Scan](/ToscaBase/ru/api-testing/api-scan-basics/). Это отдельно от аутентификации сообщения выше.
- **Message Recorder.** Его опция **Configure** принимает учётные данные прокси и умеет расшифровывать HTTPS-трафик; см. [Message Recorder](/ToscaBase/ru/api-testing/api-message-recorder/).

:::tip
Какой бы механизм вы ни использовали, сохраните прогон с `401` как негативный TestCase: он доказывает, что endpoint действительно защищён.
:::
