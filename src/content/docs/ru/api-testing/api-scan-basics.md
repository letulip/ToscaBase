Tosca тестирует веб-сервисы через **API Engine (движок API)**, а рабочий инструмент для этого — **Tosca API Scan**: отдельное окно, где вы составляете API-сообщения, отправляете их, читаете ответы и, главное, сканируете определение API, чтобы все запросы сервиса были созданы автоматически. Этот документ объясняет, зачем нужно API-тестирование, как открыть API Scan, как отправить запрос вручную и как отсканировать файл или URI определения. Превращение отсканированных сообщений в Module и TestCase описано в [TestCase для API](/ToscaBase/ru/api-testing/api-test-cases/).

## Зачем тестировать API в Tosca

API (application programming interface) позволяет двум приложениям общаться через общий формат сообщений, например XML или JSON. В ландшафте, где интегрированы, скажем, SAP, мобильное приложение, веб-портал и биллинг, каждая система отправляет API-запросы и получает ответы, а API маршрутизирует сообщения в целевую систему. API-тестирование проверяет, что эта ключевая функциональность работает **без прохода через слой UI**.

Преимущества, которые называют источники:

- Ключевую функциональность можно проверить до появления UI или пока он меняется, то есть тестирование начинается значительно раньше функционального тестирования через интерфейс.
- Частые изменения приложения перепроверяются быстро; API TestCase просты в создании и поддержке.
- Выполнение гораздо быстрее UI-автоматизации, и во время прогона не открывается никакой интерфейс.
- Отдельный мастер API Scan сканирует API самым простым способом.

Общий поток: определить детали API и функциональный сценарий по сервисам или документации, отсканировать API в API Scan и получить Module, сгенерировать и параметризовать TestCase, затем выполнить их и поделиться отчётами.

## Два способа открыть API Scan

1. **Из Tosca Commander**: откройте вкладку **API Testing** и нажмите **Start API Scan**. Мастер появляется через несколько секунд.
2. **Отдельно (standalone)**: найдите в поиске Windows `API Scan` и запустите. Tosca Commander при этом запускать не нужно.

Окно и его функции в обоих случаях одинаковы. Различия:

| | Из Commander | Standalone |
|---|---|---|
| Лицензия | Нужен Commander (лицензированный) | **Лицензия не требуется** |
| Перенос сообщений в Commander | Экспорт сразу создаёт папки в проекте Commander | Экспорт записывает файл subset (подмножество), который импортируется в Commander |

Standalone-версия рассчитана на разработчиков и API-архитекторов: они могут отправлять и проверять запросы и даже сканировать свои API без лицензии Tosca. Когда нужны верификации, параметризация и связка с UI TestCase, нужен Commander.

## Отправка запроса вручную

В левой панели дерево: проект (его можно переименовать), папки и **сообщения (messages)**. Сообщение — это один API-запрос вместе с его ответом.

1. Создайте сообщение в папке и дайте ему осмысленное имя, например `Get list of users`.
2. Выберите **метод**. Доступны все методы REST; чаще всего нужны `GET`, `POST`, `PUT` и `DELETE`.
3. Введите **endpoint (конечную точку)** и **resource (ресурс)**. Endpoint — общая часть всех запросов API; resource — уникальное расположение на сервере, откуда вы читаете или куда пишете, например `/api/users?page=2`.
4. Добавьте **payload (тело запроса)**, если метод его требует (у `GET` его нет, у `POST` обычно есть).
5. При необходимости добавьте параметры. Доступны три вида: **query**, **path** и **header**.
6. Настройте **аутентификацию**, если API защищён (Basic, OAuth 2.0, Digest, NTLM, Kerberos; см. [Аутентификация API](/ToscaBase/ru/api-testing/api-authentication/)), добавьте **вложения** или **протокол безопасности**, если применимо.
7. Нажмите **Run** вверху.

После запуска сообщение переключается с вкладки **Request** на вкладку **Response**; вернуться можно в любой момент. В ответе видны **status code (код состояния)**, например `200`, **время ответа** и **payload ответа** (в примере — JSON со всеми пользователями). О заголовках, телах и инструментах поиска, проверки и форматирования см. [Структура сообщений, SOAP и вложения](/ToscaBase/ru/api-testing/api-message-structure-and-soap/).

## Сканирование определения API

Вместо ручного ввода каждого запроса отсканируйте определение. Две кнопки в левом верхнем углу мастера:

- **File**: локальный файл определения, например WSDL, WADL, Swagger или OpenAPI (скажем, JSON-экспорт Swagger).
- **URI**: URL определения, например `swagger.json` сервиса Petstore. Поддерживаются те же форматы.

Сначала выберите папку, куда попадёт результат, затем нажмите **URI** (или **File**), введите адрес (или выберите файл) и нажмите **OK**. Секция **Advanced** диалога принимает **имя пользователя и пароль**, если само определение защищено, а также адрес **прокси** с его учётными данными.

Что даёт сканирование на примере Petstore:

- Папка с именем API (`Swagger Petstore`) и по подпапке на каждый ресурс (`pet`, `store`, `user`) — зеркало документации Swagger.
- Внутри — по сообщению на каждый тип запроса (`POST` добавить питомца, `PUT` обновить, `GET` найти по статусу и т. д.). Каждое сообщение обёрнуто в дополнительный узел; работать нужно с самим запросом.
- Endpoint, resource и метод заполнены. Тела `POST` и `PUT` содержат значения по умолчанию. У `GET` перечислены query-параметры, но **значения пустые**.

Сканирование не знает, какие значения отправлять, и не заполнит ваши учётные данные. Поэтому после сканирования заполните параметры и аутентификацию и запустите одно сообщение, чтобы убедиться, что всё работает. В примере `GET /pet/findByStatus` требует query-параметр `status`; документация допускает три значения, и `available` возвращает статус `200` со всеми доступными питомцами.

:::tip
Сканирование убирает большую часть подготовительной работы. Оно оправдано даже для ручной проверки API: вся структура папок и сообщений достаётся бесплатно.
:::

## Защищённый пример API

Часть от LambdaGeeks сканирует пример Swagger-сервиса Tricentis. В его папке `auth` лежит запрос логина: в теле передаются `user` и `password`, а в ответ приходят **token (токен)** и метка времени `expires`. Токен затем передаётся с каждым другим запросом: `GET` всех сортов кофе (пустое тело; статус `200` и список в JSON), `POST` кофе (`description`, `id` и `name` в теле), удаление или поиск кофе по `id` (`id` обязателен). Полная параметризованная версия сценария — в [TestCase для API](/ToscaBase/ru/api-testing/api-test-cases/).

:::note
В субтитрах сказано, что токен вводится на вкладке «forms» запроса; формулировка неразборчива. В уроках QASCRIPT токен передаётся как header-параметр, что по сути то же самое.
:::

## Ограничения API Scan самого по себе

Внутри API Scan можно вызвать любой запрос с данными и прочитать ответ — примерно как в Postman. Чего там нельзя: параметризовать данные, верифицировать значения и запускать сообщения как часть теста. Для этого сообщения экспортируются в Tosca Commander, где создаются API Module и TestCase: см. [TestCase для API](/ToscaBase/ru/api-testing/api-test-cases/). Чтобы захватить вызовы, которые делает приложение, вместо сканирования определения используйте [Message Recorder](/ToscaBase/ru/api-testing/api-message-recorder/).
