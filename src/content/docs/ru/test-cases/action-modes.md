ActionMode (режим действия) говорит Tosca, как применить **Value** (значение) TestStepValue к управляемому контролу: ввести, сравнить, сохранить, дождаться или использовать для сужения поиска. У каждого TestStepValue ровно один ActionMode, выбираемый из выпадающего списка в TestStep. Какие ActionMode доступны, зависит от типа интерфейса Module (GUI или не-GUI). Эта страница - справочник по всем семи; окружающие понятия описаны в [Основах TestCase](/ToscaBase/ru/test-cases/test-case-basics/).

## Сводная таблица

| ActionMode | Что делает со значением | Типичное применение | Примечания |
|---|---|---|---|
| `Input` | Вводит значение в контрол или кликает по нему | Текстовые поля, выпадающие списки, радиокнопки, кнопки, ссылки | По умолчанию для полей ввода и кликабельных контролов |
| `Insert` | Создаёт объект в не-UI структуре | XML и другие не-GUI интерфейсы | Недоступен для GUI Module |
| `Verify` | Сравнивает свойство контрола со значением | Точки проверки | Логируется с ожидаемым и фактическим значением |
| `Buffer` | Сохраняет значение контрола под именем буфера, указанным в Value | Переиспользование значений позже в том же или другом TestCase | Value - это имя буфера |
| `WaitOn` | Ждёт, пока условие в Value не станет истинным | Динамическая синхронизация | Ограничен таймаутом в настройках; показан на жёлтом фоне |
| `Select` | Выбирает узел в иерархии | Узлы таблицы, строки и колонки | Tosca ставит автоматически на пути к ячейке |
| `Constraint` | Ограничивает поиск под вышестоящим узлом элементами, соответствующими значению | Выбор строки таблицы по содержимому ячейки | Комбинируйте несколько, чтобы совпадение было уникальным |

## Input

`Input` - ActionMode, который Tosca подставляет для любого поля ввода или кликабельного контрола. Что писать в Value, зависит от контрола:

- **Текстовое поле.** Вводимый текст.
- **Выпадающий список.** Одно из значений из списка ModuleAttribute; XScan захватывает варианты при сканировании Module, так что вы выбираете из них, а не печатаете.
- **Радиокнопка, чекбокс.** Устанавливаемое состояние.
- **Кнопка или ссылка.** `X` выполняет клик внутренне, без перемещения указателя. `{CLICK}` выполняет физический клик мышью с движением курсора. Предпочитайте `X`; почему - см. [Синхронизация вместо ожиданий](/ToscaBase/ru/best-practices/synchronisation-not-waits/).

Значения могут быть выражениями, а не литералами: случайные значения, даты, строковые операции и буферы `{B[name]}` - всё это допустимый ввод. См. раздел [Выражения](/ToscaBase/ru/expressions/).

## Insert

`Insert` существует только для не-UI интерфейсов; GUI Module его не предлагают. Он создаёт объекты внутри структуры вроде XML-документа. Случай XML описан в [XML engine](/ToscaBase/ru/engines/xml-engine/).

## Verify

`Verify` сравнивает свойство контрола с ожидаемым значением. Выпадающий список Value показывает доступные свойства (`Exists`, `Enabled`, `Visible`, `InnerText` и другие), а вы дописываете условие, например:

- `Exists == True` проверяет, что контрол есть на странице.
- `Enabled == True` проверяет, что кнопка кликабельна.
- `InnerText == jane@example.com` проверяет отображаемый текст ссылки или ячейки.

Если условие выполнено, TestStepValue проходит; иначе TestStep и TestCase падают. В ExecutionLog появляется запись о верификации с ожидаемым и фактическим значением, и такую запись дают только шаги `Verify` - одна из причин, почему каждый TestCase должен содержать хотя бы один (см. [Структура TestCase](/ToscaBase/ru/best-practices/test-case-structure/)). Проверка по интервалам, регулярным выражениям и многоязычным альтернативам описана в [Интервалах и выражениях проверки](/ToscaBase/ru/expressions/intervals-and-verification-expressions/).

## Buffer

Buffer (буфер) - именованное значение, временно хранимое в Tosca Commander, чтобы переиспользовать его позже - в следующем TestStep или в другом TestCase; автор сравнивает его с глобальной переменной. ActionMode `Buffer` - один из нескольких способов создать буфер (стандартные Module из документа [Операции с буферами](/ToscaBase/ru/standard-modules/buffer-operations/) - другой).

1. Поставьте ActionMode контрола в `Buffer`. Tosca заполнит Value именем контрола; замените его на нужное имя буфера, например `email`.
2. При выполнении Tosca читает текущее значение контрола и сохраняет его под этим именем. Лог сообщает, что буфер с таким именем установлен в такое-то значение.
3. Читайте его где угодно динамическим выражением `{B[email]}`. При вводе `{B` в Value показывается описание: *возвращает значение, хранящееся в указанном буфере*.
4. Буферы видны в **Settings > Engine > Buffer** как пары имя/значение и в Buffer Viewer; см. [Буферы](/ToscaBase/ru/data-and-parameters/buffers/).

**Рабочий пример (проверка логина).** Войдите (`Input` на ссылке, полях и кнопке), затем на контроле шапки, показывающем вошедшего пользователя, поставьте `Buffer` со значением `email`. Добавьте тот же Module ещё раз с `Verify` на этом контроле и значением `{B[email]}`, затем клик `Logout`. Лог показывает верификацию с ожидаемым и фактическим значением. Тот же приём проверяет значения таблицы из базы данных против приложения или наоборот.

**Динамический буфер внутри Verify.** Значение `Verify` может содержать `{XB[name]}` на месте меняющейся части: фиксированная часть проверяется, а меняющаяся одновременно сохраняется в буфер `name`. В источнике ссылка показывает номер версии; проверка `InnerText` с номером, заменённым на `{XB[buffer_version]}`, проходит и оставляет `buffer_version` в Buffer Viewer. Синтаксис `{XB[...]}` объяснён в [Буферах](/ToscaBase/ru/data-and-parameters/buffers/).

## WaitOn

`WaitOn` - динамическое ожидание Tosca: прерывает выполнение, пока свойство, названное в Value, не примет указанное значение, и сразу продолжает. Tricentis рекомендует его всегда, когда вы ждёте условия в приложении или ещё не видимого контрола, вместо статического `TBox Wait`, который всегда ждёт полную длительность и замедляет каждый прогон.

- Value - условие вроде `Enabled == True` или `Exists == True`.
- TestStepValue с `WaitOn` показан на жёлтом фоне.
- Максимальное ожидание - **Settings > TBox > Synchronization > Synchronization timeout during WaitOn**, по умолчанию 20000 мс; увеличивайте или уменьшайте по необходимости. Если условие не выполнено за таймаут, шаг падает.

**Рабочий пример (obstacle 33678).** Клик по `Calculate` запускает индикатор прогресса, а `Send` становится доступной только когда индикатор заполнится. Три шага: `Calculate` → `X` (`Input`); `Send` → `Enabled == True` (`WaitOn`); `Send` → `X` (`Input`). Прогон ждёт ровно до момента, когда кнопка станет доступной, и продолжит работать, если время загрузки потом изменится. Полная аргументация против статических ожиданий - в [Синхронизации вместо ожиданий](/ToscaBase/ru/best-practices/synchronisation-not-waits/).

## Select

`Select` выбирает конкретный узел в иерархии. Вручную его ставят редко: когда управляют отсканированной таблицей, Tosca автоматически назначает `Select` узлу таблицы и узлу строки на пути вниз к ячейке. Строка выбирается через `$1` для первой, `$last` для последней или `$n` для строки *n*; колонки адресуются по заголовкам, захваченным XScan. Сторону Module см. в [Табличных контролах](/ToscaBase/ru/modules/table-controls/).

## Constraint

`Constraint` ограничивает поиск под вышестоящим узлом (обычно строкой таблицы) элементами, чьё значение совпадает. Вместо перебора строк и сравнения ячеек вы объявляете, какие значения ячеек идентифицируют строку, и Tosca находит её напрямую; на сотнях строк это ещё и намного быстрее. На одной строке можно комбинировать любое число ограничений, и нужно столько, сколько требуется для уникального совпадения.

**Рабочий пример (проверить email в таблице).**

1. Отсканируйте страницу и оставьте в Module только таблицу.
2. В TestStep раскройте таблицу и строку (`Select` ставится автоматически) и выберите ячейку `First name`. Поставьте ей ActionMode `Constraint` со значением `InnerText == Jane`.
3. Выберите ячейку `Email` с ActionMode `Verify` и значением `InnerText == jane@example.com`.

Прогон находит строку с именем Jane и проверяет её email; лог показывает выбранную строку и верификацию. Если две строки имеют одно имя (`John Doe` и ещё один `John`), одно ограничение падает, потому что строка не уникальна. Добавьте второе ограничение на `Last name` = `Doe`; с двумя ограничениями Tosca находит строку, и проверка проходит.

**Чтение ячейки после ограничения.** В примере LambdaGeeks первая колонка ограничена значением `Worldwide cover`, а ячейка под колонкой `Gold` поставлена в `Buffer` со значением `buffer_gold`; лог подтверждает, что буфер создан со значением ячейки. Constraint плюс `Buffer` извлекает, Constraint плюс `Verify` проверяет. Больше табличных приёмов - в [Препятствиях: таблицы](/ToscaBase/ru/troubleshooting/obstacles-tables/).

:::note
В транскрипте LambdaGeeks для ограничиваемой ячейки говорится о выборе «cell label as $1»; урок QAScript показывает `$1` как селектор строки. Селекторы строк относятся к строкам, а не к ячейкам; формулировка в первом источнике неясна.
:::

## Выбор ActionMode

- Нужно воздействовать на приложение: `Input` (GUI) или `Insert` (не-GUI).
- Нужно узнать, что что-то прошло: `Verify`.
- Значение понадобится позже: `Buffer`; нужно и то и другое сразу: `Verify` с `{XB[...]}`.
- Нужно дождаться приложения: `WaitOn`, никогда не статическое ожидание.
- Работа внутри таблицы: `Select` (автоматически) до строки, `Constraint` для её выбора, затем `Verify`, `Buffer` или `Input` на целевой ячейке.

Смешивать ActionMode в одном TestStep - норма; табличный пример использует `Select`, `Constraint` и `Verify` вместе.
