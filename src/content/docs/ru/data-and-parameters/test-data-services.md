**Test Data Services (сервисы тестовых данных, TDS)** — компонент Tosca Server для управления тестовыми данными: центральное хранилище, где TestCase регистрируют созданные данные, ищут готовые к использованию, помечают их использованными и передают следующему процессу. Эта страница описывает концепцию и веб-интерфейс; модули TBox, которые управляют TDS из TestCase, — в [Модулях Test Data Service](/ToscaBase/ru/data-and-parameters/test-data-service-modules/).

## Зачем управлять тестовыми данными

Создавать и хранить тестовые данные просто (Excel, база данных, XML, JSON, генераторы случайных значений). Управлять ими — нет:

- Каждому выполнению нужны **уникальные** данные. Повторная регистрация с тем же e-mail падает, потому что приложение его уже знает.
- Бизнес-процесс охватывает **несколько приложений**; данные, созданные веб-фронтендом, должны попасть в бэкенд и обратно без ручного копирования.
- Ручное отслеживание, какая запись использована в каком цикле, медленно и ненадёжно.

TDS отвечает на это одним местом, где данные регистрируются после создания, выбираются для прогона, где отслеживается и обновляется **состояние** каждого элемента на протяжении жизненного цикла и где элементы делятся между процессами: процесс 1 создаёт элемент и сохраняет его, процесс 2 находит, изменяет и снова сохраняет, процесс 3 продолжает.

## Где работает TDS

TDS устанавливается **вместе с Tosca Server**; ничего дополнительного не нужно. Откройте стартовую страницу Tosca Server (в видео это `http://localhost:` и порт сервера) и перейдите в **Test Data Management**. Бэкенд — база данных: по умолчанию SQLite, хранится как файл `.db` в локальной папке под program data Tosca Server, либо Microsoft SQL Server или Oracle для общей установки. См. [Tosca Server](/ToscaBase/ru/administration/tosca-server/).

Всё описанное ниже можно делать в веб-интерфейсе **или** из Tosca Commander стандартными модулями. Интерфейс — для изучения и сопровождения; в реальном проекте данные готовят сами TestCase перед запуском.

## Репозитории, типы и элементы

У TDS собственные **репозитории**, не связанные с репозиториями workspace. При первом открытии уже есть `Data Repository`. Думайте в терминах базы данных: репозиторий — база, **тип (type)** — таблица, **элемент (item)** — строка, а столбцы — атрибуты элемента.

### Создание репозитория

1. **Create repository**, введите **имя** без пробелов и спецсимволов, например `TestRepository` или `SampleApp`.
2. Выберите базу данных. **SQLite** создаёт файл локально; для **MSSQL** или **Oracle** укажите URL сервера, базу, пользователя, пароль и схему либо вставьте строку подключения.
3. **Test connection**; индикатор подключения подтверждает успех.
4. Добавьте описание и нажмите **Save**. Авторизацию можно включить, но настраивается она на стороне конфигурации сервисов Tricentis, не здесь.

:::tip
Если **Save** остаётся неактивной, возможно, файл базы с таким именем уже существует или сервису нужно обновление: перезагрузите страницу и снова проверьте подключение.
:::

Репозитории можно редактировать (имя, описание) и удалять; при удалении можно удалить и связанную базу.

### Типы

Откройте репозиторий и **добавьте тип**. Как делить типы — решать вам: по функциональности, по процессу, по приложению, по команде. Тип `Users` с именем, фамилией, e-mail и прочим — типичный пример; в видео используются `Vehicle` и `Automo` для демо страхования автомобилей. Тип должен существовать (или быть создан модулем), прежде чем в нём можно хранить элементы.

### Элементы

Внутри типа можно:

- **Импортировать** элементы из файла (выбрать или вставить) либо загрузить образцы Tricentis: выберите категорию и образец вроде `Names International 500` или `Airlines` и нажмите **Add**; тип `Users` тогда содержит около 500 записей с именем, фамилией, полом, регионом. Показан JSON; другие форматы не демонстрируются.
- **Add item**: появляется новая строка, заполните атрибуты и кликните в стороне, чтобы зафиксировать.
- **Lock / unlock** строку, чтобы другой процесс не взял её, пока она используется.
- **Удалить** строку.
- **Экспортировать** тип в CSV, Excel или JSON, выбрав кодировку, перевод строки и разделитель, и импортировать файл в другой тип.

## Предпосылки в Tosca Commander

Прежде чем выполнится любой модуль TDS, TestCase должен видеть два Test Configuration Parameter, иначе шаг падает:

| Параметр | Значение |
|---|---|
| `TestDataEndpoint` | Адрес сервера и `/testdataservice`, с портом, если он не стандартный (значение предзаполнено, поправьте хост и порт) |
| `TestDataRepository` | Имя репозитория TDS, например `SampleApp` |

Создайте их в **Configurations** проекта (среди предустановленных есть конфигурация `Test Data Service`) или во вкладке **Test Configuration** папки с TestCase; лучше всего на уровне корня или компонента, чтобы каждый TestCase их наследовал. См. [Test Configuration Parameters](/ToscaBase/ru/data-and-parameters/test-configuration-parameters/).

:::note
В видео endpoint заканчивается на «slash test data service», а порт назван на слух; написание `/testdataservice` следует предзаполненному значению, которое принимает автор. Сверьтесь с предзаполненным значением в вашей установке.
:::

## Чтение значений TDS в TestStep

Когда модуль *предоставил* (provide) элемент (см. страницу модулей), любое TestStepValue может читать его атрибуты через `{TDS[тип.атрибут]}`, например `{TDS[vehicle.engine]}` или `{TDS[vehicle.status]}`. Tosca подсвечивает корректно написанное выражение; если подсветки нет, синтаксис неверен. Используйте его прямо как значение `Input` полей, которым принадлежат данные, или скопируйте в буфер через `TBox Set Buffer`, чтобы увидеть в логе.
