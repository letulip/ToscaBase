**TestCase-Design (дизайн тест-кейсов, TCD)** — подход Tosca, при котором тестовые данные хранятся отдельно от технической части TestCase. Данные лежат в TestSheet (тестовых листах) раздела TestCase-Design; TestCase становится шаблоном, который читает из листа; Tosca генерирует по одному конкретному TestCase на каждый набор данных. Изменение данных больше не означает правку TestCase, а один шаблон даёт столько TestCase, сколько строк в листе. Команды, которые пропускают этот раздел и строят TestCase напрямую в разделе TestCases, теряют основу, вокруг которой построена Tosca.

## Зачем проектировать до того, как строить

TestCase-Design переносит в инструмент две классические техники функционального тестирования: **разбиение на классы эквивалентности** (equivalence partitioning) и **анализ граничных значений** (boundary value analysis). Цель у обеих одна: минимальное число TestCase, которое всё ещё покрывает приложение и его главные риски, потому что перебрать все значения всех полей за спринт невозможно.

Возьмём поле, принимающее числа от 1 до 2000 (поле *Engine performance* демо-приложения *Vehicle Insurance* отклоняет 12000 с предупреждением, что число должно быть между 1 и 2000). Проверить 2000 значений нельзя, поэтому:

- **Классы эквивалентности** делят значения на разделы: меньше 1, от 1 до 2000, больше 2000. Достаточно одного-двух значений на раздел (0, 200, 2500): если работает 200, ожидается, что 500 и 1000 тоже работают.
- **Граничные значения** добавляют значения на краях каждого раздела — 1, 2, 2000, 2001, — потому что ошибки в коде скапливаются вокруг границ.

В Tosca эти техники становятся свойствами экземпляров (характер valid / invalid / straight-through, позиция inner / boundary) и комбинаторными методами, которые генерируют из них экземпляры TestCase. См. [Экземпляры и комбинаторика](/ToscaBase/ru/test-case-design/instances-and-combinatorics/).

## Объекты раздела TestCase-Design

| Объект | Роль |
|---|---|
| **Folder (папка)** | Логически группирует TestSheet и классы, обычно по папке на приложение или компонент. |
| **TestSheet (тестовый лист)** | Список данных для всех комбинаций сценария. Похож на лист Excel; объект верхнего уровня раздела. |
| **Attribute (атрибут)** | Параметр данных, как правило по одному на поле приложения или бизнес-объект (тип пользователя, товар, способ оплаты). Атрибуты вкладываются на любую глубину. Не бизнес-релевантные атрибуты содержат комментарии и описания; атрибут типа *result* — ожидаемые результаты. |
| **Instances (коллекция экземпляров)** | Содержит экземпляры атрибута, то есть все значения, которые он может принимать. |
| **Instance (экземпляр)** | Одно значение атрибута; создаётся на уровне TestSheet, атрибута или класса. |
| **Экземпляр TestSheet** | Экземпляр самого листа. Каждый из них — TestCase: он выбирает по одному значению на атрибут, а его имя становится именем сгенерированного TestCase. |
| **Class (класс)** | Как TestSheet, но для повторного использования: общие атрибуты и данные, нужные нескольким листам. |
| **Class reference (ссылка на класс)** | Связь TestSheet с классом, создаётся перетаскиванием. |

Иерархия: TestSheet содержит атрибуты, экземпляры и ссылки на классы; класс содержит атрибуты и экземпляры; атрибут может содержать вложенные атрибуты и экземпляры.

:::note
В уроке Part 10 среди объектов TestCase-Design упомянуты ещё «шаги» (TestSheet «может содержать TestSteps», «шаг может содержать шаги и атрибуты»). Ни в одном из исходных видео они не показаны, поэтому здесь не описываются.
:::

## Порядок работы

1. **Создайте TestSheet** в папке раздела TestCase-Design и добавьте атрибуты для параметров данных сценария ([TestSheet и атрибуты](/ToscaBase/ru/test-case-design/test-sheets-and-attributes/)).
2. **Создайте экземпляры** для каждого атрибута, затем экземпляры самого листа — по одному на TestCase. Для каждого экземпляра листа выберите значение по каждому атрибуту или позвольте Tosca сгенерировать комбинации ([Экземпляры и комбинаторика](/ToscaBase/ru/test-case-design/instances-and-combinatorics/)).
3. **Вынесите общие данные в класс** и ссылайтесь на него из листов, которым он нужен ([Классы дизайна](/ToscaBase/ru/test-case-design/design-classes/)).
4. **Преобразуйте TestCase в шаблон**, перетащите на него TestSheet и замените жёстко заданные значения ссылками на атрибуты листа.
5. **Инстанцируйте** шаблон. Tosca создаёт по одному TestCase на экземпляр листа с данными этого экземпляра. **Реинстанцируйте** при каждом изменении листа или шаблона ([Шаблоны и инстанцирование](/ToscaBase/ru/test-case-design/templates-and-instantiation/)).
6. **Выполните** сгенерированные TestCase из ExecutionList ([Списки выполнения](/ToscaBase/ru/execution/execution-lists/)).

Полный проход по демо-приложению *Vehicle Insurance* — в [Разборе: от начала до конца](/ToscaBase/ru/test-case-design/worked-example-end-to-end/).

:::tip
Раздел TestCase-Design можно открыть плавающим окном поверх раздела TestCases. Тогда перетаскивание TestSheet на шаблон или атрибута в значение TestStep становится одним движением вместо переключения между разделами.
:::

## Преимущества и цена

Преимущества:

- Динамические данные и объекты легко обрабатываются, данные переиспользуются между TestCase.
- Никакого скриптинга; данные и технические компоненты остаются раздельными.
- При изменении данных TestCase не правятся, а генерируются заново.
- Покрытие планируется по технике дизайна — именно это ожидают услышать на собеседовании на вопрос «как вы строите TestCase»: начать в TestCase-Design, построить шаблон, сгенерировать TestCase.

Цена, по словам автора Part 10: раздел сложен и «немного дорог», а его интерфейс требует времени на освоение. Ведущий живой сессии согласен, что новичкам эта часть даётся труднее всего, из-за чего некоторые команды её пропускают.
