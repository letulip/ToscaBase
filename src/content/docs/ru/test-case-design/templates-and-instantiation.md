**TestCase template (шаблон TestCase)** — мост между спроектированным TestSheet и конкретными TestCase. Когда несколько TestCase имеют одну последовательность TestStep и отличаются только данными, вы моделируете последовательность один раз как шаблон, привязываете его к источнику данных и даёте Tosca **инстанцировать** его: по одному сгенерированному TestCase на экземпляр TestSheet со значениями этого экземпляра. К обычному TestCase TestSheet привязать нельзя; шаблон обязателен. Проектирование листа описано в [TestSheet и атрибуты](/ToscaBase/ru/test-case-design/test-sheets-and-attributes/) и [Экземпляры и комбинаторика](/ToscaBase/ru/test-case-design/instances-and-combinatorics/).

## Преобразование TestCase в шаблон

1. Постройте TestCase как обычно. Пример урока 55, `Validate login`, состоит из четырёх шагов: открыть URL (берётся из Test Configuration Parameter), `Login user` (имя, пароль, кнопка входа), `Validate error message` (поле ошибки в ActionMode `Verify`) и `TBox Window Operation`, закрывающий браузер.
2. В многопользовательском рабочем пространстве сделайте check-out TestCase.
3. Правой кнопкой по TestCase **> Convert to Template**. Символ `T` на иконке помечает шаблон. Шаблон нельзя выполнить; он существует для генерации TestCase.

Правой кнопкой **> Convert to TestCase** превращает шаблон обратно в обычный TestCase.

У шаблона важны два свойства:

- **Schema path (путь к схеме)**: источник данных, определяющий схему шаблона. Это может быть TestSheet из раздела TestCase-Design или лист Excel. После привязки свойство показывает имя листа.
- **Instance name (имя экземпляра)**: шаблон именования сгенерированных TestCase. По умолчанию они называются по экземплярам TestSheet; ведущий живой сессии ввёл шаблон, начинающийся с `TC`, и после реинстанцирования все сгенерированные TestCase получили имена по нему.

## Привязка TestSheet

Перетащите TestSheet из раздела TestCase-Design на шаблон. Это задаёт schema path, а лист становится **schema definition (определением схемы)** шаблона. Чтобы убедиться в привязке, щёлкните шаблон правой кнопкой **> Jump to Schema Definition**: Commander откроет привязанный лист.

**Check Template** (лента или контекстное меню) проверяет шаблон по схеме: сравнивает имена, использованные в шаблоне, с именами атрибутов листа, а также проверяет условия, свойства и Test Configuration Parameters. Запускайте его при каждой привязке листа и каждом изменении шаблона. Результат — либо `No errors found in template`, либо список ошибок. **Edit schema path** открывает мастер для переключения шаблона на другой источник данных.

## Привязка значений TestStep к атрибутам

При привязке листа Tosca заполняет каждое **пустое** значение TestStep, чьё имя ModuleAttribute совпадает с атрибутом листа, ссылкой в лист — например `Process.Username` и `Process.Password` в шаге `Login user`. Уже заполненные значения не трогаются. Чтобы привязать их и любые значения с несовпадающими именами:

- **Перетащите атрибут** из TestSheet в ячейку Value значения TestStep, или
- **Наберите ссылку**: начните вводить ссылку `XL` с точкой или открывающей скобкой, и Tosca предложит атрибуты привязанного листа на выбор, например `Verification.Message` для поля ошибки, которое нужно проверить.

Замените так каждое жёстко заданное значение; шаблон с константами порождает одинаковые TestCase.

:::note
Автор урока 55 описывает набираемую форму как «excel, точка, квадратная скобка», а ведущий живой сессии — как «эта ссылка на Excel, выражение, выбирающее значение из листа Excel». Ни одно видео не показывает символы на экране достаточно чётко, чтобы привести точный синтаксис, поэтому здесь названы только части: ссылка `XL`, оборачивающая `Attribute.SubAttribute`. Предпочитайте перетаскивание.
:::

Значения из ссылки на класс привязываются так же, как атрибуты листа ([Классы дизайна](/ToscaBase/ru/test-case-design/design-classes/)).

## Инстанцирование

1. Ещё раз запустите **Check Template**.
2. Правой кнопкой по шаблону **> Create Template Instance** или выделите его и нажмите **Instantiate** на ленте TestCases (это одно и то же; есть и клавиатурное сочетание).
3. Подтвердите диалог *Start instantiation* кнопкой **Yes**.

Tosca создаёт под шаблоном папку с одним сгенерированным TestCase на экземпляр TestSheet: два экземпляра в листе дают два TestCase, сотни — сотни. Каждый TestCase несёт данные своего столбца. В примере со входом первый TestCase входит как `standard_user` и не проверяет ошибку, потому что ячейка `Message` оставлена пустой; второй использует `locked_out_user` и проверяет сообщение о блокировке. Сгенерированные имена можно править.

Перетащите папку экземпляров в ExecutionList, чтобы выполнить TestCase ([Списки выполнения](/ToscaBase/ru/execution/execution-lists/)).

## Реинстанцирование после изменений

Сгенерированные TestCase сами не следуют за последующими правками. После изменения шаблона (в уроке 56 тип данных значения пароля меняется со `String` на `Password`, чтобы он маскировался) или TestSheet (новые значения, новые столбцы) щёлкните папку экземпляров шаблона правой кнопкой **> Reinstantiate Instance** (есть и на ленте). TestCase генерируются заново, и все подхватывают изменение; никакой ручной правки по каждому TestCase. Именно это делает сопровождение дешёвым: одна правка в листе или шаблоне, одно реинстанцирование.

## Условия: шаги только в некоторых экземплярах

Без условий каждый сгенерированный TestCase содержит все TestStep шаблона. В примере со входом валидный TestCase для `standard_user` всё ещё содержит шаг `Validate error message`; с пустым значением он ничего не делает при выполнении, но загромождает TestCase и путает того, кто его читает. Когда в шаблоне много шагов, ход каждого экземпляра должен следовать бизнес-логике: шаг входит в экземпляр только тогда, когда выполняется условие на данных листа.

1. В шаблоне откройте **Column Chooser** и добавьте столбец **Condition (условие)** (двойной щелчок или перетаскивание в заголовок).
2. Выделите TestStep, который должен стать условным (`Validate error message`), и заполните его ячейку Condition. Рекомендуемый способ — перетаскивание, а не набор текста: откройте TestSheet, раскройте экземпляры атрибута, от которого зависит логика (`Process.Username`), и перетащите экземпляр `locked_out_user` в ячейку. Tosca сама запишет условие в форме *атрибут равен значению* (ведущий читает его как `Process.Username == locked_out_user`). Набрать тот же текст вручную можно, но легко ошибиться.
3. Иконка шага меняется: условный TestStep показывает две стрелки с двумя точками, обычный — просто стрелки.
4. **Реинстанцируйте** экземпляры. Шаг теперь есть только в тех TestCase, чей столбец удовлетворяет условию: TestCase заблокированного пользователя сохраняет `Validate error message`, TestCase стандартного пользователя его теряет.

Условие можно сформулировать с любой стороны: *username равен locked_out_user*, чтобы включить шаг для случая с ошибкой, или *username не равен standard_user*. Условия работают и на папках, поэтому шаблон может содержать альтернативные ветки, и каждый экземпляр получает только ту ветку, которую выбирают его данные. Этот приём на примере *Vehicle Insurance* — в [Разборе: сквозной живой проект](/ToscaBase/ru/troubleshooting/worked-example-live-project/), шаг 2.

:::note
Урок 57 показывает генерацию условия перетаскиванием, но субтитровый транскрипт лишь зачитывает результат. Считайте форму с `==` выше пересказанной, а не проверенной; создавайте условия перетаскиванием экземпляров и сверяйте сгенерированный текст в столбце Condition.
:::
