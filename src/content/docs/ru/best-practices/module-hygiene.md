Module (модули) — самая объёмная часть workspace (рабочего пространства) Tosca и объекты, которые чаще всего создают небрежно. Две практики Tricentis держат их под контролем: сканировать только нужные ModuleAttribute (атрибуты модуля) и разбивать их на Module по функциональности, а также регулярно находить и сливать дубликаты Module. Обе нацелены на одни и те же проблемы: размер workspace, скорость выполнения и трудозатраты на поддержку.

## Ограничивайте ModuleAttribute и разбивайте Module по категориям

При сканировании страницы через XScan соблазнительно выбрать все контролы, чтобы Module годился для любого будущего TestCase без пересканирования. Источник сравнивает два способа сканировать страницу `Enter Vehicle Data` демо-приложения страхования — форму с обязательными и необязательными полями плюс шапкой и подвалом страницы:

- **По категориям.** Module `Headers`, содержащий только ссылку `Automobile`, и Module `Enter Vehicle Data` с полями формы.
- **Монолитно.** Один Module со всеми контролами страницы.

Монолитный Module выглядит переиспользуемым, но неэффективен:

- **Размер workspace.** Каждый отсканированный контрол хранится независимо от того, используется ли он в TestCase, и workspace растёт.
- **Скорость выполнения.** Чтобы кликнуть по ссылке `Automobile` через монолитный Module, Tosca должна пройти по всем его ModuleAttribute, чтобы найти нужный; через Module `Headers` с одним атрибутом — нет.
- **Читаемость TestCase.** Module по категориям переносят свою структуру в TestCase: каждый TestStep — один Module, и последовательность шагов читается как поток. С одним Module во всех шагах вы будете переименовывать каждый TestStep вручную.

Правило: сканируйте только контролы, нужные TestCase, и складывайте их в Module по функциональности приложения (страница, шапка, форма). Когда более позднему TestCase нужен контрол, который вы не сканировали, пересканируйте окно и добавьте контрол в существующий Module, а не создавайте новый; см. [Пересканирование Module](/ToscaBase/ru/modules/rescan-modules/) и [XScan](/ToscaBase/ru/modules/xscan/).

## Сливайте дубликаты Module

Дубликат Module — это повторное сканирование экрана, у которого Module уже есть. В одиночку их создают редко: вы знаете, что уже отсканировали. В команде они появляются постоянно: Module названы не по [соглашению об именовании](/ToscaBase/ru/best-practices/naming-conventions/), коллега не может найти нужный среди сотен или не уверен, что существующий делает то, что обещает имя, — и отсканировать заново быстрее, чем искать. Каждое из этого — ошибка, и вместе они дают workspace с несколькими копиями каждого экрана.

Цена растёт со временем:

- Размер workspace растёт, пока не становится неуправляемым; Tosca загружается медленно, выполнение замедляется.
- Каждое изменение экрана нужно применять к каждой копии, поэтому трудозатраты на миграцию и поддержку умножаются.
- Разные участники команды используют разные копии, и исправление в одной не доходит до остальных.

В Tosca для этого есть **Module merge assistant** (помощник слияния модулей), и рекомендуется запускать его по расписанию, а не только когда что-то сломалось. Он находит Module с теми же ModuleAttribute (в источнике — два скана формы входа `Swag Labs`), вливает исходный Module в целевой, перепривязывает все использования исходного в TestCase к целевому и удаляет исходный, так что вручную ничего править не нужно. Целевой Module сохраняет свои атрибуты; сохраняет ли он и собственное имя или получает имя исходного — в этом источники расходятся. Процедура, диалог конфликтов и эта оговорка — в [Дубликатах и слиянии Module](/ToscaBase/ru/modules/duplicate-and-merge-modules/).

:::caution
Помощник слияния находит только Module с совпадающими атрибутами. Дубликаты, отсканированные с разным набором контролов, он не покажет; их ловят соглашение об именовании и [процесс ревью](/ToscaBase/ru/best-practices/review-process/).
:::

## Почему это вопрос производительности

Обе практики сводятся к размеру workspace. Workspace с раздутыми и продублированными Module медленно стартует, медленно выполняет тесты и дольше синхронизируется в многопользовательской конфигурации. Держать Module компактными и уникальными — самая дешёвая доступная оптимизация производительности, и она должна быть в чек-листе каждого ревью.
